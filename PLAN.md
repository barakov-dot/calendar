## 1. Цель и границы

**Что делаем:** внутренний сервис бухгалтерской компании (≈40 клиентов, несколько бухгалтеров):
- бухгалтер видит календарь налоговых сроков по своим компаниям, вносит суммы, **сам ставит статусы «Оплачено» / «Сдано»**;
- клиент через Telegram видит свои платежи и отчёты (что, сколько, до какого числа, оплачено ли) и получает напоминания о платежах;
- по умолчанию клиент **только смотрит**; бухгалтер может включить конкретному клиенту право «Отмечать оплату сам» — для тех, кто платит налоги самостоятельно;
- повторяющиеся напоминания (свои задачи) для бухгалтера и/или клиента;
- доступ через Telegram Mini App и через сайт (один фронтенд);
- бот работает через SOCKS5-прокси (настраивается в вебе);
- все настройки приложения хранятся в JSON-файле и редактируются через веб.

**Что НЕ делаем (сознательно):**
- не считаем налоги сами (суммы вводит бухгалтер), не интегрируемся с 1С/банками;
- не ведём событийные задачи (приём/увольнение, больничные, отпуска) — бухгалтер заводит их как свои задачи;
- нет публичной регистрации и оплаты — только приглашения;
- нет массового импорта клиентов — компании вносятся вручную по ИНН через DaData.

**Режимы налогообложения клиентов:** ОСНО, УСН 6% («доходы»), УСН 15% («доходы минус расходы»), АУСН, Патент — для ООО и ИП.

## 2. Инфраструктура: Docker, Mac → Ubuntu

### 2.1. Окружения
| | Разработка | Продакшен |
|---|---|---|
| Машина | macOS, Apple Silicon M5 (arm64), Docker Desktop | Ubuntu, x86_64 (amd64), Docker Engine + compose plugin |
| Запуск | `make dev` | `make prod` |
| Бот | long polling (через SOCKS5, если включён) | long polling (через SOCKS5, если включён) |
| Веб | `http://localhost:5173` (Vite), API `http://localhost:8000` | `https://<домен>` через Caddy |
| Вход | dev-логин (выбор пользователя) + вход через бота | только Telegram (Mini App / вход через бота) |
| Mini App в Telegram | опционально через туннель (cloudflared/ngrok) | по HTTPS-домену |

### 2.2. Сервисы docker compose
```
db        postgres:16, volume pgdata, healthcheck pg_isready
api       FastAPI (uvicorn), зависит от db (healthy); миграции при старте (alembic upgrade head)
bot       aiogram long polling (тот же образ backend, другая команда)
worker    APScheduler-рассылки (тот же образ backend, другая команда)
frontend  dev: vite dev server | prod: собирается в статику и копируется в Caddy
caddy     только prod: HTTPS (Let's Encrypt), статика фронта, reverse proxy /api -> api:8000
```
Общие volume: `pgdata`, `./config` (settings.json → в api, bot, worker), `./data` (производственный календарь), `./rules`.

### 2.3. Файлы
- `docker-compose.yml` — общая часть: `db`, `api`, `bot`, `worker`, сети, volume, `env_file: .env`.
- `docker-compose.dev.yml` — монтирует `./backend` в контейнеры, `uvicorn --reload`, `watchfiles` для bot/worker, `frontend` с Vite (`node_modules` в именованном volume `frontend_node_modules`), порты `5432`, `8000`, `5173` наружу, `APP_ENV=dev`.
- `docker-compose.prod.yml` — `restart: unless-stopped`, без монтирования кода, наружу только `80/443` у Caddy, `APP_ENV=prod`, лимиты логов (`json-file`, `max-size: 10m`).
- `backend/Dockerfile` — `python:3.12-slim`, зависимости через `uv` или `pip` из `requirements.txt` / `pyproject.toml`, непривилегированный пользователь.
- `frontend/Dockerfile` — multi-stage: `node:22-slim` (dev и build) → артефакт `dist/` для Caddy.
- `deploy/Caddyfile`, `deploy/DEPLOY.md` (пошаговая инструкция для Ubuntu), `deploy/backup.sh`.

### 2.4. Совместимость arm64 → amd64
- Только мультиархитектурные официальные образы; никаких `platform:` в compose.
- Зависимости Python — с колёсами для `manylinux` aarch64 и x86_64 (asyncpg, pydantic-core, cryptography — есть для обеих).
- Образы на сервере собираются там же (`docker compose build`), с Mac образы не переносим.
- `make check-amd64` — `docker buildx build --platform linux/amd64` для backend и frontend; запускать перед каждым деплоем (на Mac работает через эмуляцию, медленно — это нормально).

### 2.5. Деплой на Ubuntu (кратко, подробно — в `deploy/DEPLOY.md`)
1. Установить Docker Engine + compose plugin, открыть порты 80/443.
2. `git clone` репозитория, создать `.env` из `.env.example`, `config/settings.json` из примера (или настроить через веб после первого входа).
3. DNS домена → IP сервера; домен прописать в `.env` (`APP_DOMAIN`) — Caddy сам получит сертификат.
4. `make prod`, затем `make migrate` (если не автоматом), проверить `https://<домен>/api/health`.
5. В BotFather: `/setmenubutton` или `/newapp` → URL Mini App `https://<домен>/`.
6. Cron: `deploy/backup.sh` раз в сутки.
7. Обновление: `git pull && make prod`.

## 3. Настройки приложения (JSON + веб)

### 3.1. Что где хранится
- `.env` — только то, что нужно до старта приложения: `POSTGRES_USER/PASSWORD/DB`, `DATABASE_URL`, `BOT_TOKEN`, `JWT_SECRET`, `ADMIN_TELEGRAM_ID`, `APP_ENV`, `APP_DOMAIN`, `SETTINGS_PATH`, опционально `TELEGRAM_PROXY_URL` (запасной прокси на первый запуск, когда веб ещё недоступен).
- `config/settings.json` — всё остальное, редактируется через веб (admin) и руками.

### 3.2. Схема `settings.json` (Pydantic-модель `AppSettings`)
```json
{
  "version": 1,
  "company": {
    "name": "ООО «Ваша бухгалтерия»",
    "support_contact": "@username",
    "timezone": "Europe/Moscow",
    "privacy_policy_url": ""
  },
  "telegram": {
    "bot_username": "my_buh_calendar_bot",
    "mini_app_url": "https://calendar.example.ru/",
    "proxy": {
      "enabled": false,
      "type": "socks5",
      "host": "",
      "port": 1080,
      "username": "",
      "password": "",
      "rdns": true
    }
  },
  "dadata": {
    "enabled": true,
    "api_key": "",
    "secret_key": "",
    "timeout_seconds": 10
  },
  "notifications": {
    "digest_time": "09:00",
    "digest_workdays_only": true,
    "default_client_offsets_days": [7, 3, 1],
    "remind_on_due_day": true,
    "fill_amount_workdays_before": 5,
    "overdue_notify": true
  },
  "tasks": {
    "generation_horizon_months_ahead": 15,
    "client_can_unmark_own_paid_hours": 24,
    "show_notices_to_clients": true
  }
}
```
- Значения по умолчанию — в Pydantic-модели; если файла нет, он создаётся из дефолтов при старте `api`.
- Миграции схемы: поле `version`; при росте версии — функция апгрейда в `settings_store`.

### 3.3. `settings_store` (backend/app/core/settings_store.py)
- `get_settings() -> AppSettings` — кеш в памяти + проверка `mtime` файла (не чаще раза в 2–5 с).
- `update_settings(patch, user)` — валидация, бэкап старой версии в `config/backups/`, атомарная запись (`tmp` → `fsync` → `os.replace`) под `fcntl.flock`, права `600`, запись в `audit_log` (без значений секретов).
- `subscribe(callback)` — для `bot` и `worker`: при изменении секции `telegram.proxy` пересоздать сессию aiogram и переподключить polling без перезапуска контейнера.
- Если JSON битый (правили руками) — лог ошибки + уведомление админу в Telegram, работаем на последней валидной версии из памяти/бэкапа.

### 3.4. Страница «Настройки» (только admin)
Вкладки:
1. **Telegram и прокси** — включить прокси, тип (socks5), хост, порт, логин, пароль. Кнопка **«Проверить подключение»** → бэкенд делает `getMe` через указанный прокси (без сохранения) и показывает результат: ✓ «Бот @name доступен, задержка 340 мс» или ошибку («нет соединения с прокси», «неверный логин/пароль», «прокси отвечает, но Telegram недоступен»). Кнопка «Сохранить» активна только после успешной проверки (или с явным подтверждением «Сохранить без проверки»). Статус бота: подключён / ошибка, время последнего успешного запроса.
2. **DaData** — API-ключ, секретный ключ, кнопка «Проверить» (тестовый запрос по ИНН), включено/выключено. Если выключено — карточка компании заполняется вручную.
3. **Уведомления** — время дайджеста, дни напоминаний по умолчанию, «заполните сумму за N рабочих дней», просрочки.
4. **Компания** — название, контакт поддержки (показывается клиентам), часовой пояс.
5. **Производственный календарь** — какие годы загружены, загрузить JSON на год.
6. **Резервные копии настроек** — список бэкапов, «Восстановить».

Секреты отдаются в API маской (`"password": "••••"`, `"has_password": true`); пустое поле при сохранении = не менять, кнопка «Очистить» — явно удалить.

### 3.5. Telegram через SOCKS5
- `services/telegram/factory.py`: `build_session(settings) -> AiohttpSession(proxy="socks5://user:pass@host:port")` (зависимость `aiohttp-socks`); без прокси — обычная сессия. Приоритет: `settings.json` (если `enabled`) → `TELEGRAM_PROXY_URL` из `.env` → напрямую.
- Используется ботом (polling), воркером (рассылки) и эндпоинтом проверки. Логин/пароль в логи не пишутся.
- **Long polling**, а не webhook: прокси работает только для исходящих запросов к Telegram, а при polling весь трафик исходящий. При старте бот вызывает `deleteWebhook`.
- Устойчивость: при ошибке сети — экспоненциальный ретрай (1, 2, 5, 10, 30 с…); при недоступности дольше 5 минут — запись в статус на странице настроек; сообщения воркера остаются в очереди (`notifications_log` со статусом `pending`) и уходят после восстановления.
- DaData и всё остальное ходят **без** прокси.
- Mini App прокси не касается: страницу открывает Telegram-клиент пользователя с вашего домена.

## 4. Модель предметной области

### 4.1. Режимы
«ИП» — **тип лица**, а не режим. Патент применяется только ИП и обычно **совмещается** с УСН или ОСНО. Поэтому у компании:
- `entity_type`: `ooo` | `ip`
- `main_regime`: `osno` | `usn6` | `usn15` | `ausn_income` | `ausn_income_expense`
- `patents[]`: список патентов (только ИП) с датами начала/окончания
- `nds_payer`: bool (для УСН — доход выше порога освобождения; для ОСНО — по умолчанию true)
- `has_employees`: bool
- `profit_advances_mode` (только ОСНО ООО): `quarterly` | `monthly_by_quarter` | `monthly_actual`
- `has_property_tax`, `has_transport_tax`, `has_land_tax`: bool (ООО)

### 4.3. Права доступа
```
get_accessible_company_ids(user):
  admin      -> все компании
  accountant -> companies where accountant_id = user.id
  client     -> company_members where user_id = user.id
```
- клиенту отдаются только `client_visible = true` — платежи, отчёты, уведомления в ФНС — со статусами; поле `comment` клиенту не отдаётся никогда;
- статусы ставит бухгалтер (или админ); клиент по умолчанию — только просмотр;
- клиент с `can_mark_paid = true` может перевести **платёжную** задачу `planned → paid`; статус ставится сразу, бухгалтеру — уведомление с кнопкой «Отменить отметку»;
- флаг `can_mark_paid` — у каждого клиента свой; меняет только бухгалтер компании или админ; изменение — в `audit_log`;
- бухгалтер не видит компании другого бухгалтера (проверка на каждом эндпоинте + тест).

| Действие | admin | accountant (своя компания) | client | client с `can_mark_paid` |
|---|---|---|---|---|
| Видеть задачу | все | все | только `client_visible` | только `client_visible` |
| Менять сумму, срок, видимость | ✓ | ✓ | — | — |
| Ставить «Оплачено» платежу | ✓ | ✓ | — | ✓ (только `planned → paid`) |
| Снимать «Оплачено» | ✓ | ✓ | — | только своё, в течение 24 ч |
| Ставить «Сдано» / «Не требуется» | ✓ | ✓ | — | — |
| Настройки приложения | ✓ | — | — | — |

## 5. Налоговые правила (движок)

### 5.1. Формат — `rules/2026.yaml`
Типы расписаний:
- `monthly` — день N месяца со смещением `month_offset`
- `quarterly` — по кварталам (`quarters: [1,2,3]` или `[4]`)
- `yearly` — раз в год, фиксированные день/месяц
- `nds_thirds` — квартальная сумма → 3 платежа до 28-го числа каждого из 3 месяцев после квартала
- `handler: <имя>` — Python-функция (патент, НДФЛ за 23–31 декабря и т.п.)

```yaml
- code: usn_advance
  title: "УСН: авансовый платёж за {period_name}"
  kind: payment
  applies: { main_regime: [usn6, usn15] }
  schedule: { type: quarterly, quarters: [1, 2, 3], day: 28, month_offset: 1 }
  needs_amount: true
  client_visible: true
  source: "п. 7 ст. 346.21 НК РФ"

- code: nds_payment
  title: "НДС за {period_name}: платёж {part} из 3"
  kind: payment
  applies: { nds_payer: true }
  schedule: { type: nds_thirds, day: 28 }
  needs_amount: true
  client_visible: true
  source: "п. 1 ст. 174 НК РФ"
```

### 5.2. Разбивка НДС
- Бухгалтер вводит **одну сумму НДС за квартал**.
- Система создаёт/обновляет 3 платежа (`part=1,2,3`), сроки — 28-е число 1-го, 2-го и 3-го месяцев после квартала (с переносом).
- Деление по 1/3 в копейках с округлением вниз, остаток — в 3-й платёж: 100 000,00 ₽ → 33 333,33 / 33 333,33 / 33 333,34.
- Ручная правка любой части → `amount_overridden = true`, автопересчёт её больше не трогает.
- Кнопка «Отметить все 3 части оплаченными».

### 5.3. Стартовый набор правил (ВСЕ сроки сверить с источником перед релизом!)
Общее: платежи — единым налоговым платежом (ЕНП), общий срок уплаты — 28-е число, уведомления об исчисленных суммах — 25-е. Переносы — ст. 6.1 НК РФ.

**УСН (6% и 15%), ООО и ИП**
| Код | Что | Срок |
|---|---|---|
| usn_notice | Уведомление по авансу за Q1/полугодие/9 мес | 25 апреля / июля / октября |
| usn_advance | Аванс за Q1/полугодие/9 мес | 28 апреля / июля / октября |
| usn_year_ooo | УСН за год (ООО) | декларация 25 марта, уплата 28 марта |
| usn_year_ip | УСН за год (ИП) | декларация 25 апреля, уплата 28 апреля |
| nds_* | НДС, если `nds_payer` (доход > 20 млн ₽ в 2026) | декларация 25-го после квартала, уплата 1/3 до 28-го |

Минимальный налог УСН 15% — те же сроки, что и годовой; отдельной задачи нет.

**ОСНО — ООО**
| Код | Что | Срок |
|---|---|---|
| nds_declaration | Декларация НДС | 25-е после квартала |
| nds_payment | НДС 1/3 | 28-е каждого из 3 месяцев после квартала |
| profit_declaration | Декларация по прибыли | 25-е после отчётного периода; за год — 25 марта |
| profit_advance | Авансы по прибыли (по `profit_advances_mode`) | 28-е; уведомления 25-е |
| property_tax | Налог на имущество (если есть) | авансы 28 апр/июл/окт, год — 28 февраля; уведомления 25-е |
| transport_land | Транспортный/земельный (если есть) | авансы 28 апр/июл/окт, год — 28 февраля; уведомления 25-е |

**ОСНО — ИП**
| Код | Что | Срок |
|---|---|---|
| ndfl_ip_advance | Аванс НДФЛ ИП за Q1/полугодие/9 мес | уведомление 25-е, уплата 28 апреля / июля / октября |
| ndfl_ip_year | 3-НДФЛ и налог за год | декларация 30 апреля, уплата 15 июля |
| nds_* | НДС | как у ООО |

**АУСН**
| Код | Что | Срок |
|---|---|---|
| ausn_tax | Налог при АУСН за месяц (сумму рассчитывает ФНС) | до 25-го следующего месяца |

**Патент (ИП)** — `handler: patent_payments`, из таблицы `patents`:
- ≤ 6 месяцев: вся сумма — не позднее даты окончания;
- 6–12 месяцев: 1/3 — в течение 90 календарных дней с начала, 2/3 — не позднее даты окончания.

- уведомления по страховым взносам — только за 1-й и 2-й месяцы квартала; по прибыли не создаются;
- добавлены декларация по имуществу (25 февраля), торговый сбор и уведомление по нему, туристический налог;
- добавлены бухгалтерская отчётность (31 марта, ООО), ЕФС-1 о стаже и о дополнительных взносах на накопительную пенсию;
- с периода 2027 года (425-ФЗ): транспортный, земельный и «кадастровый» налог организаций — авансы 28-го числа второго месяца после квартала, год 28 марта, без уведомлений (`rules/2027.yaml`);

- файл `rules/<год>.yaml` действует на налоговые периоды этого года; пока файла нет, задачи за год не создаются.

### 5.4. Генерация задач
- `generate_tasks(company, date_from, date_to)`, горизонт — с 1 января текущего года на `generation_horizon_months_ahead` месяцев вперёд.
- Запуск: при создании компании, при изменении её параметров, раз в сутки воркером, при загрузке нового производственного календаря.
- Upsert по `(company_id, rule_code, period_key, part)`: обновляются только `due_date`, `original_due_date`, `title`, `source_ref`.
- Правило перестало подходить: будущие `planned` без суммы — удалить; остальные — `not_required`.

### 5.5. Производственный календарь
- `data/calendar/<год>.json` → таблица `work_calendar` (`make calendar year=2027` или через страницу настроек).
- Источник — постановление Правительства о переносе выходных; для удобства — открытые сервисы (isdayoff.ru / xmlcalendar) + ручная проверка.
- Нет календаря на год → считаем рабочими пн–пт и шлём админу предупреждение.

## 6. Авторизация

### 6.1. Mini App
1. Фронт отправляет `Telegram.WebApp.initData` на `POST /api/auth/telegram-webapp`.
2. Проверка: `secret_key = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)`, `hash == HMAC_SHA256(secret_key, data_check_string)`, `auth_date` не старше 24 ч.
3. Пользователь по `telegram_id`; нет — 403 «Доступ по приглашению».
4. JWT: access ~1 ч, refresh ~30 дней.

### 6.2. Сайт — вход через бота
1. «Войти» → `POST /api/auth/login-request` → `{nonce, deeplink: t.me/<bot>?start=login_<nonce>}`.
2. Бот присылает кнопку «Войти на сайт» → подтверждение nonce для этого `telegram_id`.
3. Страница опрашивает `GET /api/auth/poll/<nonce>` (2 с, TTL 5 мин) → JWT.

### 6.3. Dev-логин (только `APP_ENV=dev`)
- `POST /api/auth/dev-login {user_id}` и страница `/dev-login` со списком пользователей и ролями — для проверки прав на Mac без Telegram.
- `make seed-dev` — тестовые данные: админ, 2 бухгалтера, 3 клиента (один с `can_mark_paid`), 5 компаний разных режимов.
- В prod эндпоинт не регистрируется; тест проверяет 404 при `APP_ENV=prod`.

### 6.4. Приглашения
- Админ → приглашение бухгалтера → `t.me/<bot>?start=inv_<token>` → роль `accountant`.
- Бухгалтер → «Пригласить клиента» в карточке компании (галочка «Клиент платит сам», по умолчанию выкл.) → при /start пользователь привязывается через `company_members`.
- Одноразовое, 7 дней, можно отозвать. Клиент может быть в нескольких компаниях, у компании — несколько клиентов.
- При первом /start — согласие на обработку ПДн (152-ФЗ) с кнопкой «Согласен» и ссылкой на политику.

## 7. Уведомления

`worker` (APScheduler, Europe/Moscow). Все сообщения — через `notifications_log` (уникальный ключ — защита от дублей; `pending` → `sent`/`failed` с ретраями). Параметры по умолчанию — из `settings.json → notifications`.

**Бухгалтеру:**
- **Утренний дайджест** по рабочим дням в `digest_time`: просроченное, сегодня, ближайшие 7 дней по его компаниям, сгруппировано по компании. Нечего сообщить — не писать.
- **«Заполните сумму»** — за N рабочих дней до срока платежа с пустой суммой.
- **«Клиент отметил оплату»** — сразу; кнопки «Открыть» / «Отменить отметку».

**Клиенту** (если `receive_reminders`):
- Только по **платежам**, за `offsets_days` (7, 3, 1) и в день срока: «ООО «Ромашка»: до 28.12 оплатить НДС за 3 кв. 2026 (платёж 3 из 3) — 33 333,34 ₽». Отчёты видны в календаре, напоминаний по ним нет.
- Кнопка «Оплатил» — только при `can_mark_paid`; всегда — «Открыть календарь».
- Задача `paid` / `not_required` — напоминания прекращаются.
- Просрочка: бухгалтеру всегда; клиенту — только при `can_mark_paid`.

**Повторяющиеся напоминания:** воркер раз в сутки разворачивает `rrule` в задачи `source=custom` на 60 дней вперёд с учётом `shift_rule`.

**Telegram:** не более ~25 сообщений/с, обработка 429 (`retry_after`), пользователь заблокировал бота → `bot_blocked = true`, бейдж у бухгалтера.

## 8. Тесты
- Движок правил: ожидаемые задачи на год по каждому режиму.
- **«Золотые» даты 2026**: уведомление по авансу УСН за I кв. → **27.04.2026**; за полугодие → **27.07.2026**; за 9 месяцев → **26.10.2026**; аванс УСН за полугодие → **28.07.2026**; НДС за II кв. → 28.07 / 28.08 / 28.09.2026 (с переносами); налог АУСН за октябрь → **25.11.2026**. Эталоны — 1С:ИТС «Сроки сдачи отчётности и уплаты налогов в 2026 году», календарь «Главной книги».
- Разбивка НДС (копейки, остаток, ручное переопределение); идемпотентность генерации.
- Права: изоляция бухгалтеров; клиент не видит `client_visible=false`, чужие компании и поле `comment`.
- `can_mark_paid`: без флага → 403; с флагом — `paid` + уведомление бухгалтеру; нельзя менять отчёт, сумму, чужое «Оплачено»; отмена своей отметки — только 24 ч; флаг одного клиента не даёт прав другому клиенту той же компании.
- `initData`: валидная, подделанная, просроченная подпись.
- `settings_store`: атомарная запись, бэкап, битый JSON → работа на последней валидной версии, маскирование секретов в API, «пустое поле = не менять».
- Прокси: сборка сессии с socks5 / без; приоритет settings.json → .env → direct; эндпоинт проверки возвращает понятные ошибки (мок).
- Dev-логин недоступен при `APP_ENV=prod`.

## 9. Интерфейс (Mini App = сайт)
Адаптивный, тема из Telegram (`themeParams`), в браузере — светлая/тёмная.

**Бухгалтер / админ:**
1. **Сегодня** — просроченное, сегодня, неделя; фильтры: компания, тип, статус.
2. **Календарь** — месяц/список, цвет — статус.
3. **Компании** — список с бейджами (режим, НДС, сотрудники, «нет клиента в боте», «клиент заблокировал бота», «есть задачи без суммы»).
4. **Карточка компании** — реквизиты (DaData), параметры режима, патенты, задачи, повторяющиеся напоминания, блок **«Клиенты»**: у каждого переключатели «Клиент платит сам» и «Получает напоминания», «Пригласить» / «Отвязать».
5. **Добавить компанию** — ввести ИНН или название → подсказки DaData → выбор → реквизиты заполняются → мастер (тип лица, режим, НДС, сотрудники, патенты, имущество) → генерация задач. Без DaData — ручной ввод.
6. **Задача** — срок (и исходный, если перенос), сумма, статус, кто и когда поставил (бухгалтер/клиент), внутренний комментарий, комментарий для клиента, источник, видимость клиенту.
7. **Массовые действия** — «Оплачено» / «Сдано» / «Не требуется» по выбранным задачам.
8. **Мои настройки** — время дайджеста, дни напоминаний.
9. **Админ** — бухгалтеры (пригласить, деактивировать), переназначение компаний, журнал действий, **Настройки приложения** (раздел 3.4).

**Клиент** (просмотр; «Оплатил» — только при `can_mark_paid`):
1. **Мои платежи** — «до 28 декабря — 33 333,34 ₽ — НДС», статус «К оплате» / «Оплачено ✓» / «Не требуется».
2. **Календарь** — платежи и отчёты; у отчётов «Сдано ✓» / «Готовится».
3. **История**.
4. Переключатель компаний.
5. Настройки — дни напоминаний.
6. Контакт бухгалтера / поддержки (из `settings.json → company.support_contact`).

**Команды бота:** `/start`, `/today`, `/week`, кнопка меню «Открыть календарь».

## 12. Нефункциональные требования
- Персональные данные — на сервере в РФ (152-ФЗ, локализация).
- Все изменения задач, компаний, прав клиентов и настроек — в `audit_log` (секреты — без значений).
- В каждой задаче — ссылка на источник; дисклеймер «Сроки сформированы автоматически, итоговое решение — за бухгалтером».
- API < 300 мс на типовых списках; индексы `(company_id, due_date)`, `(status, due_date)`.
- Логи в stdout (JSON-формат в prod), ротация через docker logging driver.

## 13. Открытые вопросы (решить до фазы 4)
Решено:
- сумма видна клиенту сразу после ввода;
- клиент видит уведомления в ФНС; отключается настройкой `tasks.show_notices_to_clients` (все клиентские выборки — через `client_task_condition`);
- авансов по имуществу, транспорту и земле у клиентов нет (признак компании, по умолчанию выключен); имущество разделено на среднегодовую и кадастровую стоимость; ИП получают напоминания о транспортном и земельном налоге;
- по умолчанию ежемесячные авансы по прибыли по прошлому кварталу, помесячно по факту — настройка компании;
- уведомления: по торговому сбору есть, по взносам ИП, патенту и прибыли нет, по страховым взносам только за 1–2 месяцы квартала;
- патент ровно на 6 месяцев — 1/3 и 2/3; на АУСН без сотрудников взнос на травматизм не платят, задачи по НДФЛ отключаются настройкой;
- разовые сроки, региональные праздники и отсрочки не нужны;
- нужна роль «помощник бухгалтера» с правом только просмотра (объём прав уточнить, см. Фазу 5);
- сальдо ЕНС клиенту и нигде в сервисе не показываем и не вводим;
- есть клиенты с имуществом, транспортом, землёй, торговым и туристическим сбором — признаки и правила добавлены;
- статусы ставит бухгалтер; клиент по умолчанию только видит календарь и получает напоминания;
- «Отмечать оплату сам» — для каждого клиента отдельно; отметка сразу ставит «Оплачено», бухгалтер может отменить;
- клиент видит платежи и отчёты со статусами, напоминания — только по платежам;
- бот через SOCKS5 (long polling), настройки в JSON + веб, DaData — ключи в настройках;
- разработка на Mac M5 в Docker, прод — Ubuntu x86_64; импорта клиентов нет.

Осталось решить: вопросы по срокам — в `rules/questions-2026.yaml` (дублируются в выгрузке Excel).
